**AI Clinical History Kiosk for Indian Public Hospital OPDs (incl. AYUSH)**
Builder: 1 person + Antigravity agent missions. Single source of truth — supersedes the 48h 2-person v3 brief and the earlier Solo brief.

## 1. Build Model & Ground Rules

- No Person A / Person B split. You are the sole product owner and integrator.
- The **root agent** (your main Antigravity conversation thread) acts as the sole executor: it works each mission in sequence, validates the output, and runs verification before merge.
- Antigravity runs scoped **missions**, each with a defined exit criterion (§10), an owned slice of the codebase, and a required diff review by you before merge — especially for the three spine modules: adaptive interview branching, OCR field-extraction, hospital data shape.
- Missions with genuinely independent, bounded scopes (Block 1's hospital-selection UI vs. consent flow; Block 4's AYUSH screens vs. OCR pipeline) can be worked in either order, since neither depends on the other's output. The spine modules — interview branching (Block 2) and summary assembly (Block 6) — are strictly serial: run directly by the root agent, one step depending on the last, never split apart.
- Long blocking setup work (dependency installs, migrations) runs in the background so it doesn't stall progress on other scaffolding tasks.
- One running `.agent/types/` schema file (§5) is the source of truth every mission reads from.
- Test OCR and voice flows via Antigravity's browser/artifact surface with real uploads and real mic prompts — never mock these two.

Status/provenance badge colors map onto §8's four categories; assign consistently (e.g. `system_derived` → primary blue, `doctor_entered`/verified → success green, unverified/red-flag → danger red) — lock the exact mapping in `.agent/decisions.md` in Block 0, don't leave it to per-screen judgment later.

## 8. Design Decisions to Lock

**Patient login stays lightweight.** Real Supabase Auth is doctor/triage-only. Patients: name + dummy Aadhaar → anonymous session token. No password/OTP for patients.

**Session token format:** random **UUIDv4**, generated server-side, stored in `sessions.session_token`. **Not a JWT** — no client-side claims to verify; every patient-facing request does a single DB lookup against `sessions`. Simpler to implement correctly under time pressure and matches the "anonymous session token" intent — there's nothing sensitive enough in the token payload to justify signing/verification complexity.

**"Adaptive" = the tree actually changes.** Explicit decision tree per complaint (question N's answer determines question N+1) — a linear questionnaire with reworded headers does not qualify.

**"Real OCR" = runs on the real uploaded file, every time.** Never a pre-baked demo result swapped in behind the scenes.

**Summary highlighting = provenance badges, not AI prose.** Template fill only. AI-generated summary prose later is an explicit scope change, not something to fold in silently.

**Locked red-flag patient message (verbatim, do not improvise):**
> "Important information has been identified. Please notify hospital staff or wait for assistance."

The engine must never present a diagnosis, claim certainty, recommend treatment, or otherwise alarm the patient beyond that message.

## 10. Solo Build Plan (~60 Hours, Sequential Blocks)

### Block 0 — Foundation (Hours 0–3)
Vite+React+TS+Tailwind; Express+TS+Supabase schema. `git init` locally (no remote yet). Set up the `.agent/` folder (§3). Seed `.agent/types/schema.md` with §5. Kick off `npm install` for both frontend and backend in the background so scaffolding work isn't blocked on it. Use Stitch MCP to extract/lock the §2 design tokens as Design DNA and generate first-pass mockups for the login, hospital-select, and consent screens. `/health` check passes **locally**.
- **Endpoints:** none yet (scaffolding only)
- **Testing:** none yet

### Block 1 — Login, Hospital Selection, Session Start (Hours 3–10)
Doctor login. Hospital table seeded with §6's records + selection screen. Patient flow: language → hospital select → dummy-Aadhaar → audio consent w/ touch fallback → chief-complaint picker.
*Missions (independent, no shared files — work in either order):* `hospital-select.md` (hospital seed+selection UI) and `consent-flow.md` (dummy-ID/consent flow).
- **Endpoints:** `POST /auth/login` (doctor), `GET /hospitals`, `POST /sessions`, `GET /sessions/:id`
- **Error states:** hospital list fetch fails → show cached/last-known list with a retry banner, never a blank screen; malformed dummy-Aadhaar input → inline validation, non-blocking
- **Exit:** doctor logs in live-locally; patient reaches consent in either language, with or without mic, all persisted with a session token

### Block 2 — Adaptive Interview Engine (Hours 10–20)
Spine module — don't parallelize against itself. Branching trees for the **six fixed chief complaints: chest pain, fever, abdominal pain, headache, back pain, cough**. Voice + tap-to-answer, touch-first.
- **Endpoints:** `POST /history-facts`, `GET /history-facts?session_id=`
- **Error states:** connectivity drop mid-interview → autosave the draft locally, resume without data loss on reconnect
- **Testing:** Vitest unit tests on the branching-tree logic for all six complaints (this is the module most likely to "look right but branch wrong")
- **Exit:** two different answers to the same early question produce two different subsequent questions; fully completable via touch alone

### Block 3 — Medical History Module (Hours 20–24)
Stand-alone structured module, stored separately from interview facts.
- **Endpoints:** `POST /medical-history`, `GET /medical-history?session_id=`
- **Error states:** partial submission (session interrupted mid-entry) → items already saved remain individually queryable; no all-or-nothing transaction required
- **Exit:** submissions queryable as their own category, never merged into interview data

### Block 4 — AYUSH Mode + Real OCR Pipeline (Hours 24–35)
AYUSH toggle, five screens. Real Tesseract.js on real uploads → candidate fields for correction → original file/text/fields/corrections/status/verification preserved as distinct records.
*Missions (independent — work in either order):* `ayush-screens.md` and `ocr-pipeline.md`; review OCR's diff against a real scan yourself before merge.
- **Endpoints:** `POST /ayush-assessment`, `POST /documents` (multipart upload), `POST /documents/:id/ocr` (trigger processing), `PATCH /documents/:id/fields` (manual correction)
- **Error states:** unsupported file type or oversized upload → reject with a clear message before OCR runs; OCR failure/low confidence → preserve original, flag failure, route to manual doctor review (already a MUST, §7.7)
- **Testing:** unit tests against 2–3 fixture prescription images (known-good OCR baseline) plus Playwright (via Browser MCP) exercising a real file upload end-to-end
- **Exit:** AYUSH submits 5 facts; a real prescription image yields ≥3 correctly extractable fields; a corrupted upload preserves the original and routes to manual review

### Block 5 — Red-Flag Engine + Realtime Dashboard Alerting (Hours 35–42)
Always-on rule engine on every fact write, tagging `system_derived`. On match: save, create event, broadcast via Supabase Realtime, show the §8 locked message.
- **Endpoints:** `GET /red-flags?session_id=`, `PATCH /red-flags/:id/acknowledge`; realtime channel `red-flags:{hospital_id}` (Supabase Realtime, not REST)
- **Error states:** Realtime channel disconnects → dashboard shows a "reconnecting" banner and falls back to polling every 5s
- **Testing:** Vitest unit tests covering every rule in the engine individually — this module is deterministic by design, so untested rules are a correctness bug, not a coverage gap
- **Exit:** a red flag mid-interview appears on a second device within ~2s, no refresh; patient never sees more than the locked message

### Block 6 — Summary Assembly + Doctor Dashboard (Hours 42–50)
Template-fill summary endpoint; `PATCH` for doctor edits; hospital-scoped patient list; patient-facing "submitted, please wait" screen. Dashboard implementing the §13 rule with provenance badges, inline edit, verify checkboxes, access to original documents.
- **Endpoints:** `POST /summary/:session_id/generate`, `GET /summary/:session_id`, `PATCH /summary/:session_id/fields/:field_id`, `GET /patients?hospital_id=`
- **Error states:** generation hits a required-but-missing field → surface which of the nine sections is incomplete and block "finalize" until resolved, without blocking dashboard viewing of what's already assembled
- **Exit:** every fact under its correct one of nine sections with correct provenance; hospital filter scoped correctly; nothing bleeds between sections unlabeled

### Block 7 — Hindi Text Pass + Voice Enhancement (Hours 50–54)
Every core screen from centralized language files, zero hardcoded English. Hindi voice (`hi-IN` or Bhashini) layered on top as enhancement.
- **Endpoints:** none — language files are static frontend JSON, not served via API
- **Error states:** missing translation key → fall back to the English string and log the missing key; never render a blank or broken label
- **Exit:** full patient run-through in Hindi text with zero mic access; a second run demonstrates voice as add-on, not dependency

### Block 8 — Polish, Hardening, Rehearsal, Deploy (Hours 54–60)
Error boundaries, loading/empty states, confirmed automatic mic-denied fallback everywhere, seed 1–2 canned demo patients, script and rehearse. **Then, as the final action:** add git remote, push, connect Vercel (frontend) + Railway (backend) + Supabase, verify `/health` live.
- **Endpoints:** `GET /health`
- **Error states:** any uncaught render error → global error boundary shows the calm fallback screen, session state preserved, error logged to console (never surfaced to the patient)
- **Testing:** Playwright end-to-end run (via Browser MCP) covering a full patient session, tied directly into rehearsal
- **Exit:** three consecutive clean local run-throughs, zero unhandled errors, recording saved; app live at a public URL — the only point in the build where deploy happens

## 12. Final Information Separation Rule (Doctor Dashboard)

Exactly nine sections, never silently merged:
1. Patient Information
2. Current Complaint and Adaptive Interview
3. Medical History Provided by Patient
4. AYUSH Assessment
5. Medical Documents (with access to the original uploaded file)
6. OCR-Extracted Information
7. System-Derived Information
8. Red Flags
9. Doctor Notes and Verification

This is an information collection/organization/triage-support tool for healthcare professionals — not a diagnostic or treatment system. No screen should imply otherwise.

Use them only when:
1. The task is long-running and blocking (setup, migrations)
2. The task is an independent UI screen with zero file overlap — e.g., hospital selection screen vs. consent flow screen (Block 1) touch completely different files and have no shared components

### Never Subagent (Root Agent Handles Directly)

- Adaptive interview branching (Block 2)
- Red-flag rule engine (Block 5)
- Summary assembly (Block 6)

### Subagent Workflow

1. Root agent defines mission in `.agent/missions/`
2. Subagent receives: mission file, owned file paths, exit criteria
3. Subagent executes and commits work locally
4. Subagent returns: diff, test results, exit criteria verification
5. Root agent reviews diff
6. If passed → merge; if failed → discard, root agent re-does

**Critical:** The build never depends on subagent success. If a subagent fails or produces questionable output, discard it entirely and the root agent completes the work directly.
